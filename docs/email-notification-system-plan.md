# Kusuri Mall 종합 이메일 알림 시스템 개발 계획 보고서

**작성일**: 2026년 5월 6일  
**작성자**: Manus AI  
**프로젝트**: Kusuri Mall (일본식 건강/의약품 쇼핑몰)  
**문서 버전**: v1.0

---

## 1. 개요

본 보고서는 Kusuri Mall의 이메일 알림 시스템을 5개 카테고리(회원관리, 주문/배송/결제, 문의/리뷰, 쿠폰/포인트, 이벤트)로 분류하여 종합적인 개발 계획을 수립한 문서입니다. 현재 프로젝트의 모든 사용자/관리자 페이지를 분석하여 이메일 발송이 필요한 모든 트리거 포인트를 식별하고, 각 이메일의 구현 상태와 추가 개발이 필요한 항목을 정리하였습니다.

---

## 2. 현재 시스템 분석

### 2.1 기존 이메일 인프라

현재 프로젝트에는 다음과 같은 이메일 관련 인프라가 구축되어 있습니다.

| 구분 | 파일 경로 | 역할 |
|------|-----------|------|
| 기본 이메일 발송 | `server/_core/email.ts` | Manus Email Service를 통한 이메일 발송 기본 함수 |
| 이메일 서비스 (Resend) | `server/_core/emailService.ts` | Resend API 기반 다양한 이메일 템플릿 및 발송 함수 |
| 주문 상태 이메일 | `server/_core/orderStatusEmail.ts` | 주문 상태 변경 시 이메일 발송 (확정, 준비중, 발송, 배달, 취소, 은행송금 확인) |
| 배송 알림 이메일 | `server/_core/shipmentNotificationEmail.ts` | 배송 상태 변경 시 이메일 발송 (픽업, 배송중, 배달예정, 배달완료, 실패, 반송) |
| 이메일 라우터 | `server/routers/emailRouter.ts` | 주문 확인 이메일 발송 tRPC 프로시저 |
| 이메일 서비스 (추가) | `server/services/emailService.ts` | 추가 이메일 발송 서비스 (주문 확인, 배송, 리뷰 요청) |
| 이메일 템플릿 | `server/emailTemplates/orderConfirmation.ts` | 주문 확인 이메일 HTML 템플릿 |
| 이메일 로그 | `drizzle/schema.ts` (emailLogs) | 이메일 발송 기록 저장 테이블 |
| 관리자 이메일 로그 | `client/src/pages/admin/EmailLogs.tsx` | 이메일 발송 현황 관리자 페이지 |

## 6. 기술 구현 설계

### 6.1 이메일 템플릿 구조

모든 이메일은 기존 `server/_core/emailService.ts`의 공통 레이아웃(헤더, 푸터, 래퍼)을 재사용하여 일관된 브랜드 경험을 제공합니다.

```
이메일 구조:
┌─────────────────────────────────────┐
│  [헤더] Kusuri Mall 로고 + 제목     │  ← emailHeader()
├─────────────────────────────────────┤
│  [본문] 카테고리별 컨텐츠           │  ← 각 이메일별 커스텀
│    - 인사말                         │
│    - 주요 정보 (표/카드 형태)       │
│    - CTA 버튼                       │
├─────────────────────────────────────┤
│  [푸터] 링크 + 저작권              │  ← emailFooter()
└─────────────────────────────────────┘
```

### 6.2 이메일 발송 흐름

```
트리거 이벤트 발생
    ↓
tRPC Procedure (mutation 성공)
    ↓
이메일 발송 함수 호출 (try-catch로 감싸서 실패해도 메인 로직 영향 없음)
    ↓
emailLogs 테이블에 발송 기록 저장
    ↓
Resend API / Manus Email Service를 통해 실제 발송
    ↓
발송 결과 업데이트 (sent / failed)
```

### 6.3 스케줄러 기반 이메일 (정기 발송)

다음 이메일들은 스케줄러를 통해 정기적으로 실행됩니다:

| 스케줄 | 이메일 유형 | 실행 주기 |
|--------|------------|-----------|
| 매일 09:00 | 쿠폰 만료 예정 알림 (D-3, D-1) | 1일 1회 |
| 매일 09:00 | 포인트 만료 예정 알림 (D-7, D-3) | 1일 1회 |
| 매일 09:00 | 생일 쿠폰 발급 | 1일 1회 |
| 매일 10:00 | 은행송금 기한 만료 경고 (D-1) | 1일 1회 |
| 매일 10:00 | 이벤트 종료 임박 안내 (D-3, D-1) | 1일 1회 |
| 매주 월요일 09:00 | 휴면 계정 안내 | 1주 1회 |
| 매주 월요일 09:00 | 장기 미구매 쿠폰 | 1주 1회 |
| 배달 완료 7일 후 | 리뷰 작성 요청 | 이벤트 기반 |
| 배달 완료 30일 후 | 리뷰 작성 요청 (재발송) | 이벤트 기반 |

### 6.4 관리자 이메일 설정 페이지 (신규)

관리자가 각 이메일의 활성/비활성 상태를 제어할 수 있는 설정 페이지를 추가합니다.

**기능 요구사항**:
- 카테고리별 이메일 목록 표시
- 각 이메일의 활성/비활성 토글
- 이메일 미리보기 기능
- 테스트 발송 기능
- 발송 통계 (발송 수, 성공률, 오픈율)

**관련 페이지**: `admin/EmailSettings.tsx` (신규 생성)

현재 `emailLogs` 테이블로 충분하나, 다음 테이블 추가가 필요합니다:

## 8. 이메일 수신 동의 및 법적 고려사항

일본 특정전자메일법(特定電子メールの送信の適正化等に関する法律)에 따라 다음 사항을 준수해야 합니다:

- **옵트인(Opt-in) 방식**: 마케팅 이메일(이벤트, 뉴스레터, 쿠폰 등)은 사전 동의가 필요
- **옵트아웃(Opt-out) 제공**: 모든 마케팅 이메일에 수신 거부 링크 포함 필수
- **거래 이메일 예외**: 주문 확인, 배송 알림, 비밀번호 재설정 등 거래 관련 이메일은 동의 없이 발송 가능
- **발신자 정보 명시**: 이메일에 사업자 정보(상호, 주소, 연락처) 표시 필수

**구분 기준**:

| 이메일 유형 | 분류 | 동의 필요 여부 |
|------------|------|--------------|
| 주문/배송/결제 관련 | 거래 이메일 | 동의 불필요 |
| 회원관리 (가입/비밀번호) | 거래 이메일 | 동의 불필요 |
| 문의 답변 알림 | 거래 이메일 | 동의 불필요 |
| 쿠폰/포인트 알림 | 마케팅 이메일 | **동의 필요** |
| 이벤트 안내 | 마케팅 이메일 | **동의 필요** |
| 뉴스레터 | 마케팅 이메일 | **동의 필요** |
| 재입고/가격인하 알림 | 마케팅 이메일 | **동의 필요** |

## 10. 결론

현재 Kusuri Mall은 전체 55개 이메일 알림 중 24개(44%)가 구현되어 있으며, 특히 주문/배송/결제 카테고리(76%)와 문의/리뷰 카테고리(55%)의 구현율이 높습니다. 반면 쿠폰/포인트(11%)와 이벤트(0%) 카테고리는 추가 개발이 필요합니다.

Phase 1에서는 고객 경험에 직접적인 영향을 미치는 11개 핵심 이메일을 우선 구현하고, Phase 2-3에서 마케팅 및 고객 유지를 위한 이메일을 순차적으로 추가하는 것을 권장합니다. 또한 관리자 이메일 설정 페이지와 고객 수신 동의 관리 기능을 인프라로 함께 구축하여 장기적으로 유지보수가 용이한 시스템을 구성해야 합니다.
